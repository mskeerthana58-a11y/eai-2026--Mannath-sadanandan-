# ADR-001 — durable queue, publisher confirms, manual ack, and correlationId propagation for PA2

**Status:** accepted
**Date:** 2026-09-21

## Context

Four decisions in this assignment each have a plausible-looking alternative that only reveals itself as wrong once the broker actually dies mid-flight.

Durable queue: channel.assertQueue("pa2.orders", { durable: true }) has to be declared identically on both the producer and consumer side. During implementation, the producer's publish call was initially written with the exchange and routing-key arguments swapped, which tells RabbitMQ to publish to an exchange named pa2.orders instead of routing to the queue of that name via the default exchange. Because no such exchange exists, the broker closed the channel with a 404 NOT-FOUND error, and because that error surfaced as an unhandled error event on the connection, it crashed the entire producer process. Docker's healthcheck then restarted the container in a loop, and every test that depended on the producer being reachable failed with a generic connection-refused error that gave no hint the real problem was an argument-order mistake three layers down.

Publisher confirms: POST /publish returning 202 has to mean the broker has durably received the message, not just that channel.publish() did not throw. The naive version passes every test except the fire-and-forget-vs-confirmed demonstration, which kills RabbitMQ outright right after a batch of fire-and-forget messages is confirmed present in the queue. Watching that test pass made the difference between probably queued and durably queued concrete rather than theoretical.

Manual ack: handleMessage has to append to received.jsonl before acking. Acking first and then crashing mid-write would tell RabbitMQ the message was handled when the on-disk evidence never existed.

correlationId propagation: a bug that shipped and failed the delivery test was a silent field-name mismatch: handleMessage wrote the parsed message body under the key body, while the test suite expects the key payload. The correlationId itself was propagating correctly the whole time; the bug was one hop later.

## Decision

connectProducerChannel opens a ConfirmChannel via connection.createConfirmChannel and calls channel.assertQueue with durable true. publishMessage branches on mode: confirmed mode publishes with persistent true and waits for the confirm callback before resolving, so the HTTP 202 is not sent until the broker has actually confirmed receipt; fire-and-forget mode publishes without persistent and without waiting. Both publish to the default exchange with queueName as the routing key. connectConsumerChannel declares the identical durable queue and sets prefetch to 1. handleMessage builds a record with correlationId taken from msg.properties.correlationId, writes it to received.jsonl with appendFileSync, and only then calls channel.ack, in that order.

## Alternatives considered

Using channel.publish's boolean return value as the only success signal was considered and rejected, since that value only reports local buffer state, not broker receipt. Acking before the write to received.jsonl was rejected because it could falsely acknowledge a message that was never actually recorded. Auto-ack with a low prefetch was rejected because it removes the ability to distinguish delivered from durably handled. Using the message body for correlationId instead of the AMQP property was rejected because it would require every producer to agree on a body schema just to carry routing metadata. Keeping guest/guest credentials was rejected because guest logins are loopback-only by default and would have quietly broken management-API calls used by the tests.

## Consequences

Easier: failure modes are now legible — 503 means no channel available, 202 means durably queued, and a message either appears in received.jsonl or it does not. Harder: every confirmed publish pays a real latency cost, since the HTTP response is gated on a full broker round trip. If the consumer is slow for an hour, nothing is lost since the queue is durable and prefetch is 1, but RabbitMQ's disk usage grows unbounded since nothing sets a queue length limit or TTL. Two consumers against the same queue would simply split the stream via round-robin dispatch, untested but expected to be safe given per-message ack semantics. A 100MB message body would be accepted and written as one very long line, with no size guard anywhere in this design. If RabbitMQ's disk fills up, the producer's channel-acquisition timeout would eventually surface as a 503, but only after the disk alarm state had already been reached, with no earlier warning exposed to the caller.
