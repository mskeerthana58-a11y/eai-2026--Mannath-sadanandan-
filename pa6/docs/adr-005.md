# ADR-005 — Orchestrated checkout saga where only payment and inventory can be undone

**Status:** accepted
**Date:** 2026-11-01

## Context

Checkout composes four services I do not control, in a fixed order: payment, inventory, shipping, notification. Payment has `/payment/refund` and inventory has `/inventory/release`, each with its own fail mode, so compensation can itself fail. Shipping (`/shipping/create`) and notification (`/notification/send`) have no undo endpoint at all. The assignment says a shipping or notification failure still rolls back inventory and payment, in that order, and that is the hard part: the saga can refund money for an order whose shipment already exists.

Three kinds of downstream outcome have to be told apart. A business failure is a 422 with `ok: false` and a `code` (`payment_declined`, `inventory_unavailable`, ...). A bad request is a 400 `validation_error`. A timeout is a call that has not answered within `REQUEST_TIMEOUT_MS` (2500 ms in compose); it maps to 504 + `timeout`, and 504 is reserved for that path. A timeout is not a failure I can read off the response, because the call may still have completed: the shipping mock sleeps for `shippingDelayMs` before it decides, so a timed-out shipping call can leave a real shipment behind. ## Decision

`POST /checkout` validates the `Idempotency-Key` header and the body against the canonical schema and rejects failures with 400 `validation_error`. It then derives the two values the order does not carry: `amount` is the sum of `unitPrice × quantity` computed in whole integer cents and formatted once at the end as a two-digit decimal string (`"63.90"` for the sample order, with no tax added), because the payment mock answers 400 to `"63.9"` and floats give `1889.9999999999998`; `recipient` is `customer.email`.

The saga runs in [FILL IN: function name and file], strictly sequentially, one await per step, so the tests' timestamp checks see no overlap. Every call, compensations included, appends one trace entry (`success`, `failed` or `timeout`, with start, finish and duration).

On a failure or timeout at step N, [FILL IN: compensation function name] undoes the completed steps in reverse: `inventory_release` first if inventory completed, then `payment_refund`. Shipping and notification are never compensated, because nothing exists to call. The outcome follows the table: payment failure is 422 `failed`; a later failure with a clean rollback is 422 `compensated` with the failing mock's code; the same for a timeout is 504 `compensated` with `timeout`; a failed or timed-out compensation call is 422 `failed` with `compensation_failed`, since the status enum has no state for a failed rollback.

## Alternatives considered

**Compensating endpoints for shipping and notification.** This is the option most worth writing up. With an undo for every step the saga could be exact, but it means changing services the assignment fixes, and it hides a real limit: a sent notification cannot be unsent and a shipment may already be on a truck. I accepted that those two steps cannot be rolled back and put them last, so everything that can still fail runs while the earlier steps are reversible.

**Choreography, as in PA5.** There the canonical order went out as an event and each service reacted on its own. That decouples the services, but checkout needs one synchronous answer with one status and a guaranteed order between payment and shipping. With choreography nothing owns "did this checkout succeed?", and rollback becomes services reacting to each other's failure events. The orchestrator gives one place that knows the whole state, at the price of being a single point that must be correct and that knows about every step.

**Parallel downstream calls.** Payment and inventory look independent. I rejected parallelism because strict sequencing keeps compensation simple (undo what already completed, in reverse) and because the hidden tests check ordering by timestamp. Parallel calls add the case where one has finished while the other is still in flight when the first fails.

**Hand-written request validation instead of the canonical schema.** A second copy of a course-owned schema would drift, so the scaffold validates against the schema itself. The cost is that the contract's own bound is a separate check I have to remember to enforce.

## Consequences

Rollback is easy to reason about: steps run in one order and compensation is the same list reversed. The trace shows every call that was made, and the mock `/admin/logs` endpoints let a test confirm the undo calls happened in reverse order.

What is now harder is everything the saga cannot undo. If notification fails, or shipping times out, after shipping may have succeeded, the saga refunds payment and releases inventory and reports `compensated`, while a shipment may exist. The response is honest about the rollback it performed and says nothing about the shipment it could not. I accepted that cost, because the alternative, leaving the customer charged for a failed order, is worse. [FILL IN: whether your trace or response makes the possibly-created shipment visible.] A failed refund after a later failure is the worst partial state: the customer is charged for an order that did not complete, and only `compensation_failed` in the response tells anyone.

A crash is the second weak spot. If the orchestrator is killed mid-saga, the idempotency record stays `in_progress` and, because both stores are files that survive a restart, it does not clear itself. [FILL IN: what the next request with that key gets, which on the schemas alone looks like 409 `idempotency_conflict` forever, because nothing in the record expires.] I did not add a lease or expiry, because [FILL IN: your reason].

Adding a fifth step means deciding whether it can be undone. If it can, the step list and the reverse walk change. If not, it has to go after every step that can still fail, and the shipping/notification problem above gets a third member. Two requests for the same `orderId` under different idempotency keys are not coordinated by idempotency, and the mocks do not stop it either (`reserve` just succeeds twice), so [FILL IN: whether your code guards against that or you accepted the gap]. If `REQUEST_TIMEOUT_MS` (2500 ms in compose) is set below the time a service needs to answer, for example below `SHIPPING_DELAY_MS`, every such call is a timeout, which means a rollback of an order that would have succeeded, and for shipping a shipment that exists anyway. The mocks' healthchecks (every 5 s, 3 s timeout) do not protect against this: `depends_on: service_healthy` only gates startup, so at runtime nothing stops a request reaching a mock that has just died or is restarting. That call fails as a refused connection, not a timeout, so how it is classified matters: [FILL IN: whether a refused or reset connection is treated as a failure (422) or a timeout (504), and whether it triggers compensation].
