# ADR-004 — Reliable order messaging: header correlation id, bounded retry, file-backed idempotency

**Status:** accepted
**Date:** 2026-10-25

## Context

One order must reach payment, inventory and notification independently; a consumer that is down or failing must neither lose the order nor hold up the other two. Delivery is at-least-once, so the same order can arrive twice (lost ack, a producer publishing twice, a replay). The retry topology was given: 1 s TTL retry queues that return a message through a direct exchange to the failing consumer only. Five choices were ours: where the correlation id travels, how many attempts, how to deduplicate, what counts as permanent, and what makes replay safe.

## Decision

1. **The correlation id lives in `headers.correlationId`, never in the body.** The canonical schema has `additionalProperties: false`, so a body field is a schema violation, and the body then stays byte-identical from producer to every copy in the DLQ and invalid queue. A custom header also survives every hop for free: the DLQ publish spreads `...headers` and replay uses `withoutRetryHistory(headers)`, whereas a native `properties.correlationId` would have to be set again on each republish.
2. **Three attempts (`MAX_RETRIES=3`), then the DLQ.** The attempt count is the number of `rejected` entries in `x-death`; the third failure publishes to `orders.dlq.exchange` with an `originQueue` header and acks. I kept the default rather than tuning it: with 1 s between attempts it rides out a blip of about two seconds, and anything longer is meant to end up in the DLQ for a human and a replay.
3. **notification-service deduplicates on `correlationId`, persisted in `/data/processed-ids.json`.** It is a business key (one message per order) and it also catches the same order re-published with a new message id. Order of work: append the log line, persist the id, ack, then publish the result, so a crash costs at most one duplicate log line and never a lost notification.
4. **Permanent failures:** a body that is not valid JSON (all three consumers), and valid JSON that is not an order (notification only, which needs `orderId` and `customer.email`). They go to `orders.invalid.exchange` with original bytes and headers, are acked, and are never retried or replayed. Everything else, including the simulated failure, is temporary.
5. **Replay goes through `orders.return.exchange`, routed by `originQueue`, with `withoutRetryHistory`.** Only the consumer that failed sees the message again, and with `x-death` stripped it gets a fresh three attempts. A DLQ message is acked only after it has been republished.

## Alternatives considered

- **Correlation id as a body field:** rejected, schema violation.
- **Idempotency in an in-memory `Set`:** passes the visible test but forgets everything on restart. **Redis or a database:** a new service for one consumer. **Rebuilding the set from `notification.log`:** ties dedup to the log's line format.
- **Retrying every failure:** a malformed body fails identically three times and pollutes the DLQ, where replay would fail it again.
- **Replay through `orders.exchange`:** the fanout redelivers to all three consumers, so inventory and notification would see the order twice.
- **Requeueing with `nack(msg, false, true)`:** skips the retry delay and never produces an `x-death` header.

## Consequences

- Outages longer than about two seconds always reach the DLQ and need a manual `POST /dlq/replay`.
- Only notification-service is idempotent. Replaying a payment or inventory message that half-succeeded could repeat its work; harmless here because both are simulated.
- `processed-ids.json` is rewritten whole per message, grows without bound, and only works for a single instance with `/data` mounted.
- A message with no `correlationId` header is processed by notification without deduplication; I did not make that permanent.
- A crash between the log append and persisting the id leaves one duplicate log line.
